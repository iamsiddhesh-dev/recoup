{# -- the problem --------------------------------------------------------- #}
The problem

Most merchants answer a decline with three attempts and a shrug.

Issuer declines soften, balances get topped up, OTP sessions get abandoned and retried, outages resolve. A fixed retry schedule — three attempts, fixed intervals, no regard for why it failed — recovers some money, burns customer goodwill on the rest, and cannot tell you which is which.

{% set pool = experiment.retryable_count + experiment.customer_count %}
{{ (experiment.retryable_count / pool) | pct }} can be charged again

Razorpay cannot re-run a failed payment. Charging a customer who is not present requires standing authorisation — an e-mandate, a tokenised card, a UPI Autopay mandate.

{{ (experiment.customer_count / pool) | pct }} have to be asked

For the rest the only recovery is to ask the customer again — which makes the message the recovery attempt rather than a notification about one.

The ablation

Measured, not assumed. The model is not wrong — it classifies every unresolved symptom correctly, checked against ground truth it cannot see. It is simply not worth much here: most of the failures it resolves are bank and wallet outages where the correct action is “do not chase”.

This is reported rather than fixed. The obvious way to manufacture a win would be to degrade the default until the model looks necessary; the number that produced would mean nothing.

How it decides

Each failure is a decision under uncertainty with a cost attached.

For every failure Recoup classifies a root cause from Razorpay's documented error taxonomy, then picks the action with the highest expected value. 

EV(action) = P(recover | cause, issuer, attempt_n, hour, context)
             × amount × margin
           − cost(action)
           − annoyance_penalty(customer_contact_history)
retry now retry at a modelled better time switch payment method nudge — channel, language escalate to a human stop

Every choice then passes a compliance gate with veto power: attempt caps, quiet hours, contact intervals, consent checks, mandate and risk hard-stops. The gate runs after the policy and can only subtract. Compliance is never a term inside the expected-value sum, because a rule that can be outbid by a large enough number is not a rule.

{# -- four decisions ------------------------------------------------------ #}
Four design decisions
01

A hard wall between the world and the agent

The simulator holds all ground truth; the agent sees only webhook-shaped events. A test AST-scans every module under recoup/agent/ for imports of recoup.world and fails the build.

02

An adapter seam, so the agent is portable

Simulated and test-mode adapters implement one protocol. The test-mode adapter refuses to initialise against a key that is not rzp_test_, so a live money action is structurally impossible.

03

A holdout, and then a second holdout

One baseline is what merchants do. The other isolates how much of the lift is coverage rather than judgment. Both exist to make the headline number smaller and truer.

04

An append-only ledger

Every observation, decision, veto, execution and outcome is one immutable row — SQLite triggers reject UPDATE and DELETE outright. The audit screen re-hashes each stream in front of you.

{# -- where AI is used ---------------------------------------------------- #}
Where AI is used, and where it deliberately is not

The split is not stylistic.

Razorpay documents source and step exhaustively per payment method but leaves reason open-ended. The deterministic classifier keys on what is enumerable; the model handles only what is genuinely novel.

LLM — yes
  • Unmapped free-text error → taxonomy, plus a proposed mapping rule for human review
  • Recovery copy, generated as templates in English, Hinglish and Hindi, behind a validator
  • A case narrated in prose for the merchant, from facts already in the ledger
LLM — no. Deterministic by design
  • Retry timing → empirical success model (cause × issuer × hour)
  • Action selection → expected-value argmax
  • Compliance → hard rules, no model in the loop
  • All money math → arithmetic
  • Root-cause mapping for known error codes → lookup table

It writes templates, never numbers

It produces "Your payment of {amount} did not go through"; code substitutes the real value at send time. A model that never sees an amount cannot state the wrong one. Any run of two or more digits is rejected.

Phishing-shaped copy is refused

A payment-failure message asking for an OTP, CVV or card number is indistinguishable from fraud. Copy mentioning a credential is discarded and a hand-written fallback used instead, with the rejection recorded.

{{ calls.calls | length }} model calls per run

A per-payment call would need {{ calls.per_payment_calls | int_comma }} requests per run — {{ calls.over_budget }}× Gemini Flash's daily allowance. Calls are batched instead, and responses are content-addressed and committed, so the numbers reproduce with no key and no network.

{# -- quickstart ---------------------------------------------------------- #}
Quickstart

Run it if you believe none of the above.

make reproduce re-runs the evaluation from the committed seed and compares every recorded figure — every headline here, plus a SHA-256 digest of each arm's complete event stream. It exits non-zero on any difference.

A matching digest means every decision was identical in the same order, which is stronger than matching totals: two runs can recover the same amount having done different things.

$ make setup# install
$ make eval# the arms table — no key
$ make demo# run a batch, serve at :8000
$ make reproduce# check every number above
$ make sweep# perturbed assumptions
$ make test# the wall, the rules, the EV math
{# -- what this is not ---------------------------------------------------- #}
What this is not

A measured claim about a simulated world, not a production result. Of the 29 error archetypes this simulates, one has been verified against live Razorpay test mode; the other 28 are assumptions, and the first one checked was half wrong.

The simulator cannot model whether better copy recovers more money, so the copywriter is excluded from the ablation rather than credited with a lift it has no evidence for.

The honest summary is that the method — holdout, ablation, sensitivity sweep, and a wall that makes the agent unable to cheat — would survive being pointed at real data. The numbers would move.
